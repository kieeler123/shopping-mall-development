# Day 27 --- コンポーネントの分割と責務

**中心となる問い：** このコードは、どのコンポーネントが担当すべきか？

デザインパターンを暗記するのではなく、既存のNext.js注文管理画面でコードの置き場所を判断できるようになることが目標です。

## 1. 学習目標

- ページ・一覧・カード・アイテムの責務を区別する。
- 長い、または重複したJSXを意味のある単位で分割する。
- データの所有とUI表示の違いを説明する。
- 既存の管理画面の動作を壊さずに構成を確認する。

## 2. 学習範囲

**学習範囲：**
コンポーネントの責務、ページ/一覧/カード/アイテム、UI分割、Propsの境界。

**今回扱わないこと：**
高度なデザインパターン、新しい状態管理ライブラリ、サーバーAPIの再設計、Stateのリフトアップの詳細。

## 3. プロジェクト構成

```text
AdminOrdersPage
├── ページ全体の構成
├── 読み込み中 / エラー / 空の状態
└── OrderCard（注文ごとに1つ）
    ├── 注文情報の表示
    ├── ステータス変更UI
    └── OrderItemList（その注文の商品一覧）
        └── 個々の商品表示
```

**注意：**
`OrderItemList`は`AdminOrdersPage`の直接の子ではなく、`OrderCard`の内部にあります。

## 4. 責務の分担表

| コンポーネント            | 担当すること                                                         | 担当しないこと                 |
| ------------------------- | -------------------------------------------------------------------- | ------------------------------ |
| `AdminOrdersPage`         | ページ構成、注文一覧の反復、読み込み/エラー/空の状態、フックとの接続 | カード内部の細かいマークアップ |
| `OrderCard`               | 注文1件の情報、ステータス変更UI、`OrderItemList`の配置               | 注文一覧全体の管理             |
| `OrderItemList`           | 1件の注文に含まれる商品一覧の表示                                    | 注文全体の状態変更やページ構成 |
| `useOrders`（既存フック） | 注文データと状態更新ロジックの提供                                   | カードのデザインやHTML構造     |

## 6. 段階別の学習と演習

### ステップ1 --- 現在の構造を観察

`AdminOrdersPage`で`useOrders()`と`orders.map()`を探します。`OrderCard`では注文情報とステータス用`select`を確認し、`OrderItemList`が`items`
Propsを受け取る場所を見つけます。

**ヒント：**
学習用コードで既存ファイルを上書きせず、まず現在の責務をメモしましょう。

### ステップ2 --- 責務を分類

次のコードを`AdminOrdersPage`、`OrderCard`、`OrderItemList`、`useOrders`のいずれかに分類してください。

1.  `orders.map(order => ...)`
2.  `order.name`、`order.phone`、`order.address`の表示
3.  `items.map(item => ...)`
4.  `isLoading`中の案内表示
5.  `<select value={order.status}>`の表示
6.  注文ステータスを更新する関数の提供
7.  注文が0件の場合の表示
8.  商品ごとの数量と価格の表示

**ヒント：**
ページ全体か、注文1件か、商品一覧か、データ処理かを考えましょう。

### ステップ3 --- 分割の4つの基準

① **意味：** 独立した名前を付けられるUIか？

② **重複：** 同じJSXが繰り返されているか？

③ **変更理由：** ほかの部分とは独立して変更されそうか？

④ **Propsの境界：** 必要なデータとイベントを簡潔に渡せるか？

行数が多いという理由だけで分割しないでください。

**ヒント：**
分割によってPropsが複雑になるなら、まだ分けない判断も適切です。

### ステップ4 --- 最小限のリファクタリング

**演習A：**
商品一覧が既に`OrderItemList`に分割されているか確認し、重複して作らないでください。

**演習B：**
`OrderCard`内の顧客情報が独立したまとまりなら、`OrderCustomerInfo`への分割を検討します。必ずしも新しいファイルは不要です。

**演習C：** `onStatusChange={updateOrderStatus}`の接続を維持します。

**ヒント：** 一度に1か所だけ移動し、表示と型エラーを確認しましょう。

### ステップ5 --- 検証と振り返り

`npm run lint`とプロジェクトで使う型チェック（例：`npx tsc --noEmit`）を実行します。注文一覧、ステータス選択、商品一覧が以前と同じように動作するか確認してください。

**ヒント：**
コンポーネント数を増やすことではなく、責務を明確にすることが成功です。

## 7. 責務のコード例

以下は**責務を説明するための概略コード**です。実際の型やJSXをそのまま置き換える完成コードではありません。

```tsx
// AdminOrdersPage: page-level states and the order list
const { orders, isLoading, error, updateOrderStatus } = useOrders();

{
  orders.map((order) => (
    <OrderCard
      key={order.id}
      order={order}
      onStatusChange={updateOrderStatus}
    />
  ));
}

// OrderCard: one order, including its item list
<OrderItemList items={order.items} />;

// OrderItemList: renders items for this one order
```

## 8. 確認問題

1.  ページ全体の読み込み中の条件分岐はどこに置く？

2.  注文1件のステータス`select`は誰が表示する？

3.  商品ごとの数量・価格の表示は誰の責務？

4.  `updateOrderStatus`の内部処理を`OrderCard`に移すべき？

5.  既に`OrderItemList`がある場合、同じ一覧コンポーネントを新しく作るべき？

## 9. 解答と解説

<details><summary>問題1の解答を見る</summary>

`AdminOrdersPage`。ページ全体の読み込み状態を扱うためです。

</details>

<details><summary>問題2の解答を見る</summary>

`OrderCard`。注文1件に属するUIだからです。

</details>

<details><summary>問題3の解答を見る</summary>

`OrderItemList`。1件の注文に含まれる商品の表示を担当します。

</details>

<details><summary>問題4の解答を見る</summary>

いいえ。更新ロジックは既存の`useOrders`に置き、カードはコールバックを呼びます。

</details>

<details><summary>問題5の解答を見る</summary>

いいえ。既存の分割が適切か確認し、必要な部分だけ改善します。

</details>
