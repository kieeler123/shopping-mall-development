## 문제 1 --- 렌더링 중 API 호출

``` tsx
function OrdersPage() {
  const [orders, setOrders] = useState([]);
  loadOrders();
  return <OrderList orders={orders} />;
}
```

**질문:** 왜 문제가 될 수 있는가? - ① 렌더링마다 API 요청이 발생하고
state 업데이트로 반복 렌더링이 생길 수 있다. - ② React에서는 일반 함수를
호출할 수 없다. - ③ `useState`는 API 데이터를 저장할 수 없다.

**제출 답:** ① / 이유: 반복 렌더링이 생길 수 있기 때문이다.

**채점:** 정답. **보완 설명:**
`loadOrders → setOrders → 재렌더링 → loadOrders`의 순환이 생길 수 있고,
렌더링은 순수해야 한다. 모든 상태 업데이트가 무조건 무한 루프를 만든다는
뜻은 아니다.

**팁:** 호출 위치와 그 호출이 바꾸는 state를 함께 추적한다.

## 문제 2 --- `[userId]` 의존성

``` tsx
useEffect(() => { fetchOrders(userId); }, [userId]);
```

**질문:** `userId`가 1에서 2로 바뀌면? - ① Effect는 재실행되지 않는다. -
② 커밋 이후 Effect가 다시 실행되어 새 사용자의 주문을 요청한다. - ③
컴포넌트가 무조건 삭제된다.

**제출 답:** ② / 이유: 커밋 후 Effect가 다시 실행되며 `userId`가 의존성
배열에 있기 때문이다.

**채점:** 정답. **보완 설명:** 개발자가 Effect가 읽는 `userId`를
의존성으로 선언하고 React가 이전 값과 현재 값을 `Object.is`로 비교한다.
의존성 배열이 `userId`를 Effect에 '전달'하는 것은 아니다.

**팁:** 의존성은 실행 횟수 제한 장치가 아니라 재동기화 조건이다.

## 문제 3 --- 함수 참조

``` tsx
const loadOrders = async () => {
  const response = await fetch("/api/orders");
  setOrders(await response.json());
};
useEffect(() => { void loadOrders(); }, [loadOrders]);
```

**질문:** API 요청이 반복될 수 있는 이유는? - ① 비동기 함수를 Effect에서
호출했기 때문 - ② 렌더링마다 `loadOrders`가 새 함수로 만들어져 의존성이
변경되기 때문 - ③ state가 배열이기 때문 - ④ 의존성 배열이 함수를 자동
메모이제이션하기 때문

**제출 답:** ② / 이유: 렌더링마다 함수가 새로 만들어져 의존성이 변경된
것으로 판단된다.

**채점:** 정답. **보완 설명:** 문제는 '의존성 배열 밖에 있다'가 아니라
**컴포넌트 함수 본문에서 새 함수 객체가 생성된다**는 것이다.
`Object.is(oldFn, newFn)`은 `false`가 될 수 있다. 해결은 Effect 내부로
이동하거나 필요한 경우 `useCallback`으로 참조를 안정화한다.

**팁:** 같은 코드 ≠ 같은 함수 참조.

## 문제 4 --- Effect와 이벤트 핸들러

**상황 A:** 주문 페이지에 들어가면 사용자 주문 조회. **상황 B:** 주문
취소 버튼을 누르면 취소 요청.

-   ① 둘 다 Effect
-   ② A는 Effect, B는 이벤트 핸들러
-   ③ A는 이벤트 핸들러, B는 Effect
-   ④ 둘 다 렌더링 중 직접 실행

**제출 답:** ② / 이유: A는 외부에서 가져오고 B는 보내기 때문이다.

**채점:** **선택은 정답, 이유는 보완 필요.**

**왜 기존 이유가 불충분한가?** GET도 클릭 이벤트에서 실행할 수 있고
POST도 외부 시스템 동기화의 일부일 수 있다. **API 방향(받기/보내기)이
기준이 아니다.**

**모범 답안:** A는 페이지 표시 또는 `userId` 변경에 맞춰 주문 목록을
동기화해야 하므로 Effect가 적절하다. B는 사용자가 취소 버튼을 클릭한
사건 때문에 실행해야 하므로 이벤트 핸들러가 적절하다.

**팁:** '왜 지금 실행하는가?'를 기준으로 구분한다.
