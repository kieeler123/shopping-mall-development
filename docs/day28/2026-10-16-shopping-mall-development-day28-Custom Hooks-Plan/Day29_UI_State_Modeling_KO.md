# Day 29 — UI 상태 모델링

> **핵심 질문:** 데이터가 있다는 상태 외에 UI에는 어떤 상태가 존재하는가?

- **Stack:** Next.js · React · TypeScript
- **Duration:** 90분
- **학습 방식:** Step별 학습 → 객관식 1문제 → 정답 해설 → 다음 Step. 마지막에는 주관식 중심 15문제 종합 코딩 테스트.

## 1. 학습 목표

- Loading, Error, Empty, Success의 차이를 설명한다.
- `isLoading`, `error`, `orders`로 UI 상태를 판단한다.
- `&&`, `!`, 삼항 연산자를 활용해 조건부 렌더링을 작성한다.
- UI 상태의 우선순위를 정하고 겹치는 조건을 이해한다.
- API 요청 성공·실패에 따른 화면 변화를 추적한다.
- 실제 `AdminOrdersPage`의 렌더링 조건을 분석한다.
- 직접 설명 및 TypeScript 코드 작성으로 개념을 확인한다.

> **팁:** 네 가지 상태를 이름으로만 외우지 말고, 각 상태가 되는 조건을 문장으로 설명해 보자.

## 2. 핵심 UI 상태 모델

```text
요청 시작
  ↓
Loading
  ├─ 실패 → Error
  └─ 성공
      ├─ 데이터 없음 → Empty
      └─ 데이터 있음 → Success
```

| 상태 | 조건 | UI |
|---|---|---|
| Loading | 요청 진행 중 | 주문을 불러오는 중입니다... |
| Error | 요청 실패 | 오류 메시지 |
| Empty | 요청 성공, 주문 0개 | 주문이 없습니다. |
| Success | 요청 성공, 주문 1개 이상 | 주문 카드 목록 |

> **팁:** 이 모델은 **목록 조회** 기준이다. 상태 변경(PATCH) 중이나 재시도 중처럼 추가적인 UI 상태도 존재할 수 있다.

## 4. Step별 학습 계획

### Step 1 — Day 28 복습 (10분)

- `useOrders()`가 State와 함수를 제공하는 방식 복습
- `setOrders()` 이후 React 재렌더링과 Props 전달 이해
- **객관식 문제:** `setOrders()`로 주문 배열이 바뀌면 UI가 갱신되는 이유는?

> **팁:** Hook → Page → OrderCard의 연결 경로를 말로 설명해 보자.

### Step 2 — Loading, Error, Empty, Success (15분)

- 요청 중 / 실패 / 성공 후 빈 배열 / 성공 후 데이터 존재 구분
- 각 상태에 맞는 사용자 메시지 생각하기
- **객관식 문제:** API 요청은 성공했지만 `orders.length === 0`이라면 어떤 UI 상태인가?

> **팁:** 빈 배열은 오류가 아니다. 성공했지만 표시할 항목이 없는 상태다.

### Step 3 — 조건부 렌더링 (15분)

```tsx
{isLoading && <p>주문을 불러오는 중입니다...</p>}
{error && <p>오류: {error}</p>}
{!isLoading && !error && orders.length === 0 && (
  <p>주문이 없습니다.</p>
)}
```

- `&&`, 논리 부정 `!`, 비교 연산자 `===` 이해
- 필요 시 삼항 연산자로 표현하는 방법 비교
- **객관식 문제:** `!isLoading && !error`는 어떤 상황을 의미하는가?

> **팁:** 각 조건을 `true` 또는 `false`로 바꿔 직접 계산해 보자.

### Step 4 — UI 상태 우선순위 (15분)

- Loading과 Error가 동시에 참일 때 화면이 겹칠 수 있음을 이해
- `if` / Early Return으로 명시적 우선순위 표현
- 상태를 하나로 모델링하는 방식도 개념적으로 비교하되, 라이브러리는 도입하지 않음
- **객관식 문제:** Loading과 Error가 동시에 존재할 때 어떻게 화면을 처리해야 하는가?

> **팁:** 사용자에게 어떤 상태를 먼저 알려야 하는지 결정한 후 조건식을 작성하자.

### Step 5 — 실제 프로젝트 실습 (15분)

기존 `AdminOrdersPage`의 조건을 분석한다.

```tsx
{!isLoading && !error && orders.length > 0 && (
  <div className="space-y-6">
    {orders.map((order) => (
      <OrderCard
        key={order.id}
        order={order}
        onStatusChange={updateOrderStatus}
      />
    ))}
  </div>
)}
```

- 목록 조회 성공 / 실패에 따른 렌더링 확인
- PATCH 실패 시 `error`가 설정되면 `!error`가 `false`가 되어 주문 목록이 숨겨지는 문제 분석
- 기존 기능이 정상이라면 불필요한 변경은 하지 않음
- **객관식 문제:** PATCH 오류 발생 시 주문 카드가 화면에서 사라질 수 있는 이유는?

> **팁:** 데이터가 실제로 삭제된 것인지, 조건부 렌더링으로 숨겨진 것인지 구분하자.

## 6. Step 1 시작 문제

다음 코드를 보고 답하자.

```tsx
const { orders, isLoading, error } = useOrders();
```

**문제 1.** `useOrders()`에서 `setOrders()`로 주문 배열을 변경했을 때 React UI가 갱신되는 이유는?

- A. `fetch()`가 자동으로 HTML을 수정하기 때문이다.
- B. React가 State 변경에 따라 컴포넌트를 다시 렌더링하고 새로운 Props를 전달하기 때문이다.
- C. `OrderCard`가 서버에서 직접 데이터를 다시 가져오기 때문이다.
- D. `useEffect()`가 모든 State 변경마다 자동으로 API를 호출하기 때문이다.

**정답:** B

**해설:** React가 상태 업데이트를 처리하면 관련 컴포넌트가 재렌더링되고, 변경된 `orders`에서 생성한 새 Props가 `OrderCard`에 전달된다.

> **팁:** 실제 학습에서는 정답을 먼저 가리고 풀어 보자.
