# 쇼핑몰 프로젝트 개발 원칙 및 확장 로드맵

## 1. 프로젝트 방향

이 프로젝트는 처음부터 모든 기능을 갖춘 대형 쇼핑몰을 만드는 것이 아니라,  
**작은 기능 단위로 완성하고 점진적으로 확장하는 방식**으로 진행한다.

최종 목표는 실무에서 사용되는 구조와 개념을 충분히 학습할 수 있는 수준의 쇼핑몰을 만드는 것이며,  
각 단계에서 필요한 기능만 구현하고 설계 문서는 지속적으로 업데이트한다.

### 핵심 원칙

> **설계는 미래를 고려하되, 구현은 현재 필요한 최소 크기로 한다.**

개발은 다음 사이클을 반복한다.

```text
작게 완성
↓
Git 기록
↓
문서 업데이트
↓
기능 하나 추가
↓
리팩터링
↓
다시 완성
```

> **팁**  
> 처음부터 모든 기능을 구현하려고 하지 않는다.  
> 작은 버전을 실제로 완성하고, 동작하는 상태를 유지하면서 확장하는 것이 가장 중요하다.

---

## 2. 구현 범위와 설계 범위는 다르게 가져간다

현재 구현은 작게 시작하되, 문서에서는 향후 확장 가능성을 기록한다.

### 현재 구현

```text
Product
Cart
```

### 향후 확장 예정

```text
Product
ProductVariant
Category
Cart
User
Order
Payment
Inventory
Shipment
Review
Coupon
Admin
```

즉, 문서는 미래 구조를 설명할 수 있지만 실제 코드는 현재 필요한 기능까지만 구현한다.

```text
문서 범위
████████████████████

현재 구현 범위
████
```

개발이 진행되면서 구현 범위를 점진적으로 확장한다.

```text
████
→ ███████
→ ██████████
→ ████████████████
```

> **팁**  
> 문서는 미래를 대비하고, 코드는 현재 필요한 문제만 해결한다.

---

## 3. ERD는 완성본이 아니라 살아있는 문서로 관리한다

ERD를 처음부터 완벽하게 설계할 필요는 없다.

초기에는 매우 단순하게 시작할 수 있다.

### ERD v0.1 예시

```text
Product

- id
- name
- price
- stock
```

상품 옵션이 필요해지는 시점에 구조를 확장한다.

### ERD v0.2 예시

```text
Product
   ↓
ProductVariant
```

장바구니와 주문이 추가되면 다시 확장한다.

### ERD v0.3 예시

```text
Product
   ↓
ProductVariant
   ↓
CartItem
   ↓
OrderItem
```

ERD는 다음과 같이 버전별로 관리한다.

```text
ERD v0.1
상품

ERD v0.2
상품 + 장바구니

ERD v0.3
상품 옵션

ERD v0.4
회원

ERD v0.5
주문

ERD v1.0
MVP 완성
```

> **팁**  
> ERD를 처음부터 고정된 설계도로 생각하지 않는다.  
> 현재 시스템 구조를 설명하는 문서이며, 요구사항 변화에 따라 함께 변경한다.

# 4. 버전별 개발 로드맵

## v0.1 — 최소 쇼핑몰

첫 번째 목표는 아주 작은 쇼핑몰을 완성하는 것이다.

### 구현 기능

```text
홈
상품 목록
상품 상세
장바구니
```

사용자 흐름은 다음과 같다.

```text
상품 목록
   ↓
상품 상세
   ↓
장바구니
```

### 포함하지 않는 기능

```text
회원가입
로그인
주문
결제
관리자
쿠폰
리뷰
배송
```

장바구니는 초기에는 `localStorage`를 사용할 수 있다.

### 학습 목표

```text
Next.js
Routing
React Component
Server Component
Client Component
데이터 조회
상태 관리
UI 구조
```

> **팁**  
> v0.1의 목표는 쇼핑몰 전체 완성이 아니다.  
> **처음부터 끝까지 정상 동작하는 작은 사용자 흐름 하나를 완성하는 것**이 목표다.

---

## v0.2 — 상품 구조 개선

기본 상품 구조를 조금 더 실제 쇼핑몰에 가깝게 확장한다.

### 데이터 구조

```text
Product
ProductImage
Category
```

### 추가 기능

```text
카테고리
상품 검색
상품 정렬
페이지네이션
```

> **팁**  
> 새로운 기능이 생겼다고 무조건 테이블을 추가하지 않는다.  
> 현재 데이터 구조로 해결 가능한지 먼저 검토한다.

---

## v0.3 — 상품 옵션 도입

색상, 사이즈 등의 상품 옵션을 추가한다.

### 기존 구조

```text
Product
```

### 변경 구조

```text
Product
   ↓
ProductVariant
```

예시:

```text
Premium Hoodie

Black / S
Black / M
Black / L

Gray / S
Gray / M
Gray / L
```

각 Variant는 다음과 같은 데이터를 가질 수 있다.

```text
SKU
Color
Size
Price
Stock
Status
```

장바구니 역시 상품 자체가 아닌 Variant를 바라보도록 변경한다.

```text
기존

CartItem
 └─ product_id
```

```text
변경

CartItem
 └─ variant_id
```

> **팁**  
> 기능 요구사항 때문에 기존 구조가 불편해지는 순간이 리팩터링 타이밍이다.  
> 처음부터 복잡하게 만들기보다 필요해졌을 때 구조를 개선한다.

---

## v0.4 — 회원 시스템

회원 기능을 추가한다.

### 구현 기능

```text
회원가입
로그인
로그아웃
```

기존 비회원 장바구니는 다음처럼 발전할 수 있다.

```text
Guest Cart
   ↓
Login
   ↓
User Cart
```

장바구니도 필요에 따라 `localStorage`에서 DB 기반으로 이전한다.

> **팁**  
> 인증을 나중에 추가하면 로그인 기능이 기존 데이터 구조에 어떤 영향을 주는지 직접 경험할 수 있다.

---

## v0.5 — 주문 시스템

장바구니 데이터를 주문으로 변환한다.

### 구조

```text
Cart
 ↓
Order
 ↓
OrderItem
```

### 함께 학습할 개념

```text
가격 재검증
재고 확인
Order Snapshot
Transaction
서버 검증
```

상품 가격은 클라이언트가 전달한 값을 신뢰하지 않고 서버에서 다시 조회한다.

주문 상품 정보는 구매 당시 값을 별도로 보관한다.

```text
OrderItem

- product_name
- option_name
- unit_price
- quantity
- subtotal
```

> **팁**  
> 주문 기능부터는 단순 CRUD보다 비즈니스 로직 중심으로 사고한다.

---

## v0.6 — 관리자 시스템

관리자가 직접 상품과 주문을 관리할 수 있도록 한다.

### 관리자 페이지 예시

```text
/admin
/admin/products
/admin/products/new
/admin/products/[id]
/admin/orders
/admin/orders/[id]
/admin/inventory
```

### 구현 기능

```text
상품 등록
상품 수정
상품 삭제
상품 이미지 관리
옵션 관리
재고 관리
주문 조회
주문 상태 변경
```

> **팁**  
> 관리자 페이지를 만들면 CRUD, Form Validation, 권한 처리, 파일 업로드, 데이터 테이블 등을 한 번에 학습할 수 있다.

---

## v0.7 — 결제 및 재고

주문 시스템에 결제와 재고 처리를 추가한다.

### 추가 도메인

```text
Payment
Inventory
```

초기 결제는 실제 PG 대신 Mock Payment로 시작할 수 있다.

```text
READY
PAID
FAILED
CANCELLED
REFUNDED
```

재고 역시 처음에는 단순하게 시작한다.

```text
재고 = 기존 재고 - 주문 수량
```

필요해지면 다음과 같이 발전시킨다.

```text
보유 재고
예약 재고
차감 재고
재고 복원
```

> **팁**  
> 결제와 재고는 처음부터 복잡하게 만들지 않는다.  
> 실제 문제가 발생하는 단계에서 Transaction, Lock, 재고 예약 같은 개념을 추가한다.

---

# 6. 개발 진행 방식

각 기능은 다음 순서로 개발한다.

```text
요구사항 작성
   ↓
간단한 설계
   ↓
구현
   ↓
테스트
   ↓
문제 발견
   ↓
리팩터링
   ↓
문서 업데이트
```

예를 들어 처음에는 단순하게 시작한다.

```text
Product

id
name
price
```

이후 상품 옵션 요구사항이 생긴다.

```text
문제

상품 하나에
색상 / 사이즈별 가격과 재고를 관리할 수 없다.
```

그 문제를 해결하기 위해 다음 구조를 도입한다.

```text
Product
   ↓
ProductVariant
```

그리고 ERD와 Decision 문서를 업데이트한다.

> **팁**  
> 새로운 기술을 먼저 도입한 뒤 사용처를 찾지 않는다.  
> 문제가 발생했을 때 해당 문제를 해결하기 위한 기술을 도입한다.

# 7. 프로젝트에서 지킬 개발 원칙

## 7.1 작은 단위로 완성한다

한 번에 여러 기능을 만들지 않는다.

```text
상품 목록 완성
↓
상품 상세 완성
↓
장바구니 완성
```

> **팁**  
> 항상 현재 브랜치가 실행 가능한 상태를 유지하는 것을 목표로 한다.

---

## 7.2 필요할 때 리팩터링한다

처음부터 모든 미래 요구사항을 코드에 반영하지 않는다.

```text
단순 구조
↓
요구사항 증가
↓
문제 발견
↓
리팩터링
```

> **팁**  
> 확장 가능성과 과도한 추상화는 다르다.  
> 아직 존재하지 않는 요구사항 때문에 복잡한 코드를 만들지 않는다.

---

## 7.3 코드 변경 이유를 기록한다

중요한 설계 변경은 `decisions.md`에 남긴다.

예:

```text
Product에 stock을 두었음
↓
옵션별 재고 요구사항 발생
↓
ProductVariant로 stock 이동
```

> **팁**  
> 최종 코드보다 코드가 왜 현재 구조로 발전했는지를 설명할 수 있는 것이 중요하다.

---

## 7.4 핵심 흐름을 먼저 완성한다

최우선 흐름:

```text
상품 탐색
↓
상품 선택
↓
장바구니
↓
주문
↓
결제
```

그 이후:

```text
리뷰
쿠폰
찜
추천
소셜 로그인
```

을 추가한다.

> **팁**  
> 핵심 사용자 흐름이 완성되기 전에는 부가기능 개발을 최대한 미룬다.

---

# 8. 최종 목표

최종적으로 다음 흐름이 완성된 쇼핑몰을 목표로 한다.

```text
회원가입
   ↓
로그인
   ↓
상품 탐색
   ↓
옵션 선택
   ↓
장바구니
   ↓
주문
   ↓
결제
   ↓
재고 처리
   ↓
주문 조회
```

관리자는 다음 흐름을 사용할 수 있도록 한다.

```text
관리자 로그인
   ↓
상품 등록
   ↓
옵션 등록
   ↓
재고 관리
   ↓
주문 확인
   ↓
주문 상태 변경
```

최종적으로는 실제 서비스 구조를 이해하고 설명할 수 있는 수준을 목표로 한다.

---

# 9. 가장 중요한 원칙

> **작게 시작한다.**
>
> **한 단계씩 완성한다.**
>
> **필요할 때 확장한다.**
>
> **구조가 바뀌는 이유를 기록한다.**
>
> **문서는 코드와 함께 계속 발전시킨다.**

처음부터 완벽한 쇼핑몰을 만드는 것이 목표가 아니다.

```text
v0.1
작지만 완성된 쇼핑몰
        ↓
v0.2
조금 더 좋은 구조
        ↓
v0.3
상품 옵션
        ↓
v0.4
회원
        ↓
v0.5
주문
        ↓
...
        ↓
v1.0
실무 수준의 MVP
```

이 과정을 직접 경험하면서 쇼핑몰이 왜 현재와 같은 구조를 가지는지 이해하는 것이 프로젝트의 가장 중요한 학습 목표다.

> **팁**  
> 최종 결과물뿐 아니라 **v0.1에서 v1.0까지 발전한 과정 자체를 프로젝트 자산으로 남긴다.**
