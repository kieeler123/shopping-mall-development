# Day 18 복습 정리 --- React 기초 연결과 독립 구현 진단

## 1. 이번 복습의 목적

이번 복습은 새로운 내용을 빠르게 진도 나가는 것이 아니라, 지금까지 배운
개념이 실제 코드에서 어떻게 연결되는지 확인하고 **혼자 작은 프로젝트를
시작할 때 어디에서 막히는지 진단하는 것**에 초점을 맞췄다.

복습 방식은 다음과 같았다.

-   개념을 기억나는 대로 설명한다.
-   작은 요구사항을 보고 직접 설계하거나 구현한다.
-   맞게 사용하지만 설명이 부정확한 개념을 구분한다.
-   한 번 교정한 내용을 다른 문제에서 다시 적용할 수 있는지 확인한다.
-   단순 문법 실수와 실제 개념 부족을 구분한다.

> **팁:** 이후 복습에서도 단순히 "코드를 본 적 있다"가 아니라, **설명할
> 수 있는가 → 직접 쓸 수 있는가 → 다른 문제에 적용할 수 있는가** 순서로
> 확인한다.

------------------------------------------------------------------------

## 2. HTML / CSS / JavaScript 역할

### HTML

웹페이지의 **구조와 콘텐츠**를 만든다.

### CSS

HTML로 만든 구조의 **표현, 배치, 디자인**을 담당한다.

### JavaScript

사용자의 행동에 반응하고 데이터를 변경하는 등 **동작과 로직**을
담당한다.

처음에는 다음과 같이 이해했다.

-   HTML = 화면에 보이는 것
-   CSS = 예쁘게 만드는 것
-   JavaScript = 기능을 추가하는 것

큰 방향은 맞지만, 조금 더 정확하게는 다음과 같다.

``` text
HTML → 구조 / 콘텐츠
CSS → 표현 / 디자인
JavaScript → 행동 / 로직
```

장바구니 추가·삭제처럼 데이터가 변경되는 기능은 HTML만으로 처리하는 것이
아니라 JavaScript 로직이 필요하다.

> **팁:** HTML/CSS/JS를 외울 때 "화면 / 꾸미기 / 기능"에서 끝내지 말고
> **구조 / 표현 / 동작**으로 한 단계 더 정확하게 기억한다.

------------------------------------------------------------------------

## 3. React를 사용하는 이유

Vanilla JavaScript에서는 상태가 바뀐 뒤 DOM을 직접 찾아 변경하는 작업이
자주 필요하다.

React에서는 **State와 UI의 관계를 선언적으로 관리**할 수 있다.

핵심 흐름:

``` text
State 변경
↓
Re-render
↓
새로운 State를 기준으로 UI 계산
↓
UI 반영
```

React의 장점은 단순히 코드를 짧게 만드는 것이 아니라 **변하는
데이터(State)와 화면(UI)의 관계를 체계적으로 관리하는 것**에 있다.

> **팁:** React를 "DOM 조작을 안 해도 되는 라이브러리" 정도로만 기억하지
> 말고, **State가 바뀌면 그 State를 기준으로 UI를 다시 계산한다**는
> 흐름으로 기억한다.

------------------------------------------------------------------------

## 4. DOM

DOM은 브라우저가 HTML 문서를 프로그래밍에서 다룰 수 있도록 **객체/트리
구조로 표현한 인터페이스**다.

JavaScript가 화면을 변경할 때 원본 HTML 파일 자체를 수정하는 것이
아니라, 브라우저 메모리에 만들어진 DOM을 조작한다.

> **팁:** `HTML 파일 = DOM`이라고 생각하지 않는다. 브라우저가 HTML을
> 해석해서 DOM 구조를 만든다고 구분한다.

# 5. useState와 Re-render

기본 형태:

``` jsx
const [count, setCount] = useState(0);
```

각 부분의 의미:

``` text
count
→ 현재 State 값

setCount
→ State를 업데이트하는 함수

0
→ 최초 State의 초기값
```

예:

``` jsx
setCount(count + 1);
```

실행 흐름:

``` text
count = 0
↓
setCount(count + 1)
↓
State = 1
↓
Re-render
↓
UI에 1 반영
```

`useState(0)`이 Re-render 때 코드상 다시 보이더라도 `0`은 최초 State
생성 시의 초기값이다. React는 이후 현재 State를 유지한다.

### 중요한 교정

`setCount`는 이전 값을 삭제하지 않고 추가하는 함수가 아니다.

``` jsx
setCount(1);
```

은 현재 State를 `1`로 업데이트하는 것이다.

또한 일반 변수도 값 자체는 변경할 수 있다. 하지만 React State를 사용하는
중요한 이유는 **컴포넌트가 기억해야 하는 변경 데이터를 관리하고, State
업데이트를 통해 Re-render와 UI 갱신을 연결하기 위해서**다.

> **팁:** `useState = 화면 값 바꾸기`라고만 외우지 말고 **컴포넌트가
> 기억해야 하는 변경 데이터 + UI 갱신 연결**이라고 이해한다.

## 6. 직접 구현했던 Counter

직접 작성한 핵심 구조:

``` jsx
import { useState } from "react";

export default function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>increase</button>
    </div>
  );
}
```

이 문제에서는 다음을 스스로 결정할 수 있었다.

``` text
변하는 값 → count
↓
State 필요
↓
초기값 0
↓
버튼 클릭 Event
↓
setCount
↓
Re-render
↓
UI 반영
```

JSX의 최상위 Wrapper와 `export default`를 잠깐 잊었지만, 이는 현재까지의
진단에서는 핵심 개념 부족보다는 문법/구조 기억 문제에 가까웠다.

> **팁:** 사소한 문법을 잠깐 잊은 것과 기능 구조 자체를 설계하지 못하는
> 것을 구분한다.

# 7. 요구사항을 정확히 코드로 옮기기

복습 과정에서 반복해서 발견된 부분이다.

### 이름 변경 문제

요구사항은:

``` text
이름: 철수
[영희로 변경] [철수로 변경]
```

이었지만 처음에는 하나의 Toggle 버튼으로 구현했다.

Toggle 자체는 올바른 코드였지만 **요구사항과 구현 결과가 달랐다.**

### 과일 목록 문제

요구사항:

``` text
장바구니
- 사과
- 바나나
[오렌지 추가]
```

처음 구현에서는:

``` jsx
{fruit.join(", ")}
```

을 사용했다.

배열 State 업데이트는 맞았지만, 요구사항은 각각의 목록 항목으로 보여주는
것이었으므로 다음처럼 `map()`으로 JSX를 만드는 것이 더 적합하다.

``` jsx
<ul>
  {fruit.map((item) => (
    <li key={item}>{item}</li>
  ))}
</ul>
```

### 진단

코드를 작성할 수 없는 것과는 다르다. 익숙한 패턴을 빠르게 적용하다가
**요구사항의 세부 UI 조건을 놓치는 경향**이 있었다.

> **팁:** 코딩 전에 요구사항을 `데이터 / 행동 / 화면 형태` 세 가지로
> 나누고, 구현 후 요구사항과 결과를 다시 대조한다.

# 8. 배열 State와 불변성(Immutability)

과일 배열:

``` jsx
const [fruit, setFruit] = useState(["사과", "바나나"]);
```

오렌지 추가:

``` jsx
setFruit([...fruit, "오렌지"]);
```

React State는 직접 수정하지 않고 **새로운 배열/객체를 만들어 Setter에
전달하는 방식**을 기본으로 한다.

피해야 할 방식:

``` jsx
fruit.push("오렌지");
```

`push()`는 기존 배열 자체를 변경한다.

반면:

``` jsx
[...fruit, "오렌지"]
```

은 기존 요소를 펼쳐 새로운 배열을 만든다.

### 중요한 교정

Spread의 의미는 "뒤에 붙인다"가 아니다.

``` jsx
[...fruit, "오렌지"]
```

에서 오렌지가 뒤에 오는 이유는 **문법의 작성 순서** 때문이다.

``` jsx
["오렌지", ...fruit]
```

이면 오렌지가 앞에 온다.

> **팁:** Spread는 "뒤에 추가"가 아니라 **배열의 요소 또는 객체의 속성을
> 펼친다**라고 기억한다.

# 9. map / filter / find

상품 데이터:

``` js
const products = [
  { id: 1, name: "맥북", price: 200 },
  { id: 2, name: "아이폰", price: 100 },
  { id: 3, name: "에어팟", price: 30 },
];
```

## map

각 요소를 원하는 형태로 변환하고 **새로운 배열을 반환**한다.

React에서는 데이터 배열을 JSX 배열로 변환할 때 자주 사용한다.

``` jsx
products.map((product) => (
  <ProductCard product={product} />
))
```

특정 상품을 변경할 때도 모든 요소를 확인하면서 조건에 맞는 요소만 새로운
값으로 바꿀 수 있다.

## filter

조건을 만족하는 요소만 남겨 **새로운 배열을 반환**한다.

삭제 예:

``` jsx
products.filter((p) => p.id !== id)
```

## find

조건을 만족하는 **첫 번째 요소 하나**를 반환한다.

없으면 `undefined`가 된다.

> **팁:** `map = 각각을 다른 형태로`, `filter = 조건에 맞는 것들만`,
> `find = 조건에 맞는 하나`로 먼저 구분하고 반환 결과가 배열인지 단일
> 값인지도 함께 기억한다.

# 10. 객체 배열 State 업데이트

처음 가장 크게 막혔던 부분 중 하나다.

목표:

``` text
에어팟 price: 30
↓
에어팟 price: 50
```

기존 배열과 객체를 직접 수정하지 않는 구현:

``` jsx
function handleChangeAirpot() {
  const updatedProducts = product.map((p) => {
    if (p.name === "에어팟") {
      return {
        ...p,
        price: 50,
      };
    }

    return p;
  });

  setProduct(updatedProducts);
}
```

각 부분의 역할:

``` text
map
→ 기존 배열을 기준으로 새로운 배열 생성

조건문
→ 변경 대상 찾기

...p
→ 기존 객체의 속성을 펼쳐 새로운 객체 구성

price: 50
→ 기존 price 속성을 새로운 값으로 덮어쓰기

return p
→ 변경 대상이 아닌 상품은 기존 객체 사용

setProduct
→ 완성된 새로운 배열로 React State 업데이트
```

### 처음 막혔던 이유

처음에는 다음 개념을 동시에 조합해야 했다.

``` text
map
+
조건
+
객체 Spread
+
불변성
+
Setter
```

구조적인 힌트를 받은 뒤에는 올바르게 완성했고, 이후 재시험에서는 힌트
없이 다음 형태까지 직접 작성했다.

``` jsx
setProduct(
  product.map((p) =>
    p.id === id
      ? { ...p, price: p.price + 10 }
      : p
  )
);
```

### 진단

개별 문법을 전혀 모르는 상태라기보다 **여러 개념을 한 번에 꺼내 조합하는
과정에서 처음 속도가 느려지는 문제**가 있었다. 하지만 한 번 교정된 뒤
새로운 문제로 전이할 수 있었다.

> **팁:** 여러 개념이 필요한 기능에서는 바로 코드를 쓰지 말고
> `대상 찾기 → 데이터 변환 → State 업데이트`로 먼저 나눈다.

# 11. Object Spread

``` js
const user = {
  name: "철수",
  age: 20,
};

const newUser = {
  ...user,
  age: 30,
};
```

결과:

``` js
{
  name: "철수",
  age: 30
}
```

객체에서 같은 속성이 여러 번 나오면 **뒤에 작성된 값이 앞의 값을
덮어쓴다.**

반대로:

``` js
const newUser = {
  age: 30,
  ...user,
};
```

이면 `...user`가 나중에 오므로 최종 `age`는 `20`이다.

``` text
Array Spread
→ 요소를 펼침

Object Spread
→ 속성을 펼침
```

> **팁:** `...` 자체가 값을 변경하는 것이 아니다. **기존 요소/속성을
> 펼친 뒤 작성 순서와 추가 코드가 최종 결과를 결정한다.**

# 12. 삭제 기능과 filter

직접 구현:

``` jsx
function handleDelete(id) {
  setProduct(
    product.filter((p) => p.id !== id)
  );
}
```

렌더링:

``` jsx
{product.map((p) => (
  <div key={p.id}>
    {p.name} : {p.price}

    <button onClick={() => handleDelete(p.id)}>
      {p.name} 삭제
    </button>
  </div>
))}
```

이 문제에서는 스스로 다음 구조를 설계할 수 있었다.

``` text
삭제 대상 식별
→ id

상품 출력
→ map

특정 상품 제외
→ filter

새 배열
→ setProduct

State 변경
→ UI 변경
```

> **팁:** 삭제는 "배열에서 직접 지운다"보다 **삭제할 항목을 제외한
> 새로운 배열을 만든다**라고 생각하면 React의 불변성과 자연스럽게
> 연결된다.

# 13. 수정 + 삭제 결합 문제

다음 기능을 힌트 없이 구현했다.

``` text
맥북 : 200 [+10] [삭제]
아이폰 : 100 [+10] [삭제]
에어팟 : 30 [+10] [삭제]
```

핵심 코드:

``` jsx
function handleAdd(id) {
  setProduct(
    product.map((p) =>
      p.id === id
        ? { ...p, price: p.price + 10 }
        : p
    )
  );
}

function handleDelete(id) {
  setProduct(
    product.filter((p) => p.id !== id)
  );
}
```

이 재시험에서는 다음 조합을 스스로 사용했다.

``` text
id
map
조건
Object Spread
Setter
filter
Event
```

즉 첫 번째 객체 배열 수정 문제에서 막혔던 내용이 이후 문제에서는 실제
구현으로 연결됐다.

> **팁:** 복습에서 한 번 틀린 것보다 **교정 후 비슷하지만 다른 문제에서
> 스스로 적용했는가**를 더 중요하게 본다.

# 14. React의 key

리스트 렌더링:

``` jsx
{products.map((p) => (
  <ProductCard
    key={p.id}
    product={p}
  />
))}
```

`key`는 React가 렌더링된 리스트 항목의 **정체성(identity)을 구분**하기
위해 사용한다.

### 중요한 구분

``` jsx
key={p.id}
```

과:

``` jsx
handleDelete(p.id)
```

에서 같은 `id`를 사용하지만 역할은 완전히 다르다.

``` text
key={p.id}
→ React가 리스트 항목을 식별

handleDelete(p.id)
→ 우리 코드가 삭제 대상 id를 함수에 전달
```

또한 JavaScript의 `map()` 자체가 `key`를 요구하는 것이 아니다.
**React에서 JSX 리스트를 렌더링할 때** key가 중요하다.

삭제/삽입/정렬이 가능한 리스트에서는 index보다 안정적인 고유 `id`를
key로 사용하는 것이 일반적으로 적합하다.

### key는 일반 Props가 아니다

``` jsx
<ProductCard
  key={product.id}
  product={product}
/>
```

에서 자식은:

``` jsx
props.product
```

는 사용할 수 있지만:

``` jsx
props.key
```

로 `key`를 일반 Props처럼 받을 수 없다.

자식에게 id 자체가 필요하면 별도의 Props로 전달해야 한다.

``` jsx
<ProductCard
  key={product.id}
  id={product.id}
  product={product}
/>
```

> **팁:** `key = 자식에게 id 전달`로 기억하지 않는다. **key는 React를
> 위한 리스트 식별 정보**다.

# 15. Event Handler와 함수 실행 시점

다음 두 코드는 다르다.

``` jsx
onClick={() => handleDelete(p.id)}
```

``` jsx
onClick={handleDelete(p.id)}
```

두 번째 코드는 렌더링 과정에서 `handleDelete(p.id)`를 **즉시 실행**한다.

인자를 전달하면서 클릭 시점까지 실행을 미루려면:

``` jsx
onClick={() => handleDelete(p.id)}
```

처럼 함수를 전달한다.

인자가 필요 없다면:

``` jsx
onClick={handleDelete}
```

처럼 함수 자체를 바로 전달할 수도 있다.

``` text
handleDelete
→ 함수 자체

handleDelete()
→ 함수 실행
```

> **팁:** Event Handler에는 "지금 실행할 결과"가 아니라 **나중에
> 이벤트가 발생했을 때 실행할 함수**를 전달한다고 생각한다.

------------------------------------------------------------------------

# 16. Props

이번 복습에서 중요한 약점이 발견된 부분이다.

처음에는 Props를:

> 프로젝트가 커지고 컴포넌트를 다른 파일로 분리할 때 필요한 것

에 가깝게 이해하고 있었다.

하지만 핵심은 **파일 분리 여부가 아니라 컴포넌트 사이의 값 전달**이다.

같은 파일 안에서도 부모와 자식 컴포넌트 사이에서 값을 전달하면 Props를
사용한다.

``` jsx
<ProductCard product={product} />
```

자식:

``` jsx
function ProductCard({ product }) {
  return (
    <div>{product.name}</div>
  );
}
```

흐름:

``` text
부모
↓ Props
자식
```

> **팁:** Props를 "다른 파일의 값을 가져오는 방법"이 아니라 **부모
> 컴포넌트가 자식 컴포넌트에게 값을 전달하는 방법**이라고 기억한다.

------------------------------------------------------------------------

# 17. 함수도 Props로 전달할 수 있다

이번 복습에서 처음에는 이 부분을 "전혀 모르겠다"고 판단했다.

부모:

``` jsx
function App() {
  const [count, setCount] = useState(0);

  function handleIncrease() {
    setCount(count + 1);
  }

  return (
    <CounterButton onIncrease={handleIncrease} />
  );
}
```

자식:

``` jsx
function CounterButton({ onIncrease }) {
  return (
    <button onClick={onIncrease}>
      +1
    </button>
  );
}
```

의미:

``` text
App
handleIncrease 함수 보유
↓
onIncrease라는 Props 이름으로 전달
↓
CounterButton
↓
버튼 클릭
↓
onIncrease 실행
↓
실제로 App의 handleIncrease 실행
↓
App State 변경
```

`onIncrease`는 React가 특별히 제공하는 이름이 아니라 우리가 정한
**Custom Prop 이름**이다.

``` jsx
onIncrease={handleIncrease}
```

은:

> `handleIncrease` 함수를 `onIncrease`라는 이름으로 자식에게 전달한다.

라고 읽으면 된다.

> **팁:** "함수 Props"를 완전히 별개의 기능으로 생각하지 않는다.
> **Props로 전달하는 값의 종류가 함수일 뿐**이다.

------------------------------------------------------------------------

# 18. 데이터 Props + 함수 Props

예:

``` jsx
<ProductCard
  product={p}
  onDelete={handleDelete}
/>
```

자식:

``` jsx
function ProductCard({ product, onDelete }) {
  return (
    <div>
      {product.name}

      <button
        onClick={() => onDelete(product.id)}
      >
        삭제
      </button>
    </div>
  );
}
```

여기서:

``` text
product
→ 화면에서 사용할 데이터 Props

onDelete
→ 자식에서 실행할 함수 Props
```

함수가 만들어진 곳과 실행되는 곳, State가 변경되는 곳을 구분해야 한다.

``` text
함수를 만든 곳
→ 부모

함수를 Props로 받은 곳
→ 자식

함수를 실행하는 곳
→ 자식의 Event

함수가 변경하는 State
→ 부모가 가진 State
```

> **팁:** `부모 함수니까 부모에서만 사용한다`고 생각하지 않는다. Props로
> 전달했다면 자식이 그 함수를 실행할 수 있다.

------------------------------------------------------------------------

# 19. 여러 단계 Props 전달

컴포넌트 구조:

``` text
App
└── ProductList
    └── ProductCard
```

`App`이 `handleDelete`를 가지고 있고 `ProductCard`에 삭제 버튼이 있다면:

``` text
App
handleDelete
↓ Props
ProductList
↓ Props
ProductCard
↓
삭제 버튼 클릭
↓
전달받은 함수 실행
↓
App의 handleDelete 실행
↓
App State 변경
```

중간의 `ProductList`가 삭제 함수를 직접 사용하지 않더라도 아래의
`ProductCard`가 필요하다면 **받아서 다시 전달**할 수 있다.

이런 중간 전달 단계가 매우 깊어지는 문제는 이후 Props Drilling과도
연결된다.

> **팁:** 컴포넌트가 여러 단계일 때는 코드부터 보지 말고 **State 위치와
> Props 이동 경로를 화살표로 먼저 그린다.**

------------------------------------------------------------------------

# 20. State는 어디에 두어야 하는가?

쇼핑몰 구조:

``` text
App
├── Header
│   └── 장바구니 개수
│
└── ProductList
    └── ProductCard
        └── 장바구니 추가
```

처음에는 `Header`에 cart State를 두는 것이 좋겠다고 판단했다.

하지만 `cart`는:

``` text
Header
→ 장바구니 개수 필요

ProductCard
→ 장바구니 추가 기능 필요

Cart
→ 장바구니 전체 데이터 필요
```

처럼 여러 컴포넌트에서 필요할 수 있다.

따라서 이 경우에는 이들을 포괄할 수 있는 공통 부모인 `App`에서 관리하는
것이 자연스럽다.

``` text
          App
       cart State
        ↙     ↘
   Header    ProductList
               ↓
           ProductCard
```

### 핵심 원칙

State를 **무조건 가장 위에** 두는 것이 아니다.

더 정확한 기준:

> 그 State를 필요로 하는 컴포넌트들의 적절한 공통 부모에 둔다.

> **팁:** `State는 최대한 위로`가 아니라 **필요한 만큼만 위로**라고
> 기억한다.

------------------------------------------------------------------------

# 21. State를 굳이 올리지 않아도 되는 경우

구조:

``` text
App
└── ProductPage
    ├── ProductImage
    ├── ProductInfo
    └── QuantitySelector
```

`quantity`를 오직 `QuantitySelector`만 사용한다면:

``` jsx
function QuantitySelector() {
  const [quantity, setQuantity] = useState(1);
}
```

처럼 해당 컴포넌트에 두면 된다.

굳이:

``` text
App
↓
ProductPage
↓
QuantitySelector
```

로 Props를 전달할 필요가 없다.

하지만 요구사항이 바뀌어:

``` text
ProductInfo
→ quantity 필요

QuantitySelector
→ quantity 필요
```

가 된다면 두 컴포넌트의 공통 부모인 `ProductPage`로 State를 올리는 것이
자연스럽다.

이것이 **State 끌어올리기(Lifting State Up)**와 연결된다.

> **팁:** State 위치는 고정된 정답이 아니다. **누가 그 데이터를 필요로
> 하는지 요구사항이 바뀌면 State 위치도 바뀔 수 있다.**

------------------------------------------------------------------------

# 22. State와 Props를 연결해서 생각하는 순서

이번 복습에서 가장 중요한 연결 중 하나다.

``` text
1. 어떤 데이터가 변하는가?
↓
State 후보 찾기

2. 누가 그 State를 사용하는가?
↓
State 위치 결정

3. 자식이 State 값을 필요로 하는가?
↓
데이터 Props 전달

4. 자식에서 부모 State를 변경해야 하는가?
↓
변경 함수 Props 전달

5. 자식에서 함수 실행
↓
부모 State 업데이트

6. Re-render
↓
새로운 Props 전달

7. UI 변경
```

> **팁:** 프로젝트를 만들 때 `useState부터 쓰자`가 아니라 **데이터 →
> 사용자 → State 위치 → Props 흐름**을 먼저 설계한다.

# 23. 현재까지 발견된 강점

이번 복습 기준으로 다음 부분은 실제 코드에서 사용할 수 있었다.

-   기본 `useState`
-   버튼 Event
-   `map`, `filter`, `find`의 기본 사용
-   배열 State에 항목 추가
-   `filter`를 이용한 삭제
-   `id`를 이용한 대상 식별
-   한 번 교정 후 객체 배열의 불변 업데이트
-   Object Spread의 덮어쓰기 순서
-   수정 + 삭제 기능 결합
-   간단한 요구사항을 State/Event/UI로 나누기
-   State를 필요한 컴포넌트 가까이에 두어야 한다는 기본 판단

> **팁:** 이미 할 수 있는 기본 문법을 처음부터 반복해서 외우는 것보다,
> 앞으로는 **여러 개념을 조합하는 문제**에서 이 지식을 꺼내 쓰는 연습의
> 비중을 높인다.

# 24. 현재까지 발견된 보강 포인트

## 24.1 개념을 정확하게 설명하는 속도가 느림

코드는 작성할 수 있지만 `왜 이렇게 작성했는가?`를 말로 설명할 때 시간이
오래 걸렸다.

특히:

``` text
map의 정확한 역할
Spread의 정확한 역할
key의 정확한 역할
Setter와 불변성의 관계
```

에서 주변 개념과 섞이는 경우가 있었다.

> **팁:** 설명할 때
> `목적 → 대상 → 데이터 변환 → State 업데이트 → UI 반영` 순서를
> 사용한다.

## 24.2 여러 개념을 처음 조합할 때 막힘

특히 객체 배열 수정에서:

``` text
map
+
조건
+
Object Spread
+
불변성
+
setState
```

를 처음부터 동시에 조합하는 데 시간이 오래 걸렸다.

하지만 구조를 한 번 이해한 뒤 비슷한 문제에서는 독립 구현에 성공했다.

> **팁:** "모른다"로 바로 판단하지 말고 **어느 단계까지 혼자
> 만들었는지**를 확인한다. 구조 힌트 후 바로 완성된다면 지식 부재보다
> 조합/인출 문제일 수 있다.

## 24.3 요구사항 세부 조건을 놓치는 경우

-   두 버튼 요구사항 → Toggle 한 버튼 구현
-   목록 UI 요구사항 → `join()`으로 문자열 출력
-   모든 상품의 삭제 버튼 → 처음에는 특정 상품명으로 버튼 Label 작성

기능 자체는 구현했지만 요구사항과 결과가 조금씩 달랐다.

> **팁:** 구현 후 반드시 **요구사항 문장과 UI를 한 줄씩 대조**한다.

## 24.4 함수 Props

이번 복습에서 가장 명확하게 발견된 보강 항목 중 하나다.

처음에는 함수 Props의 흐름을 모른다고 했고, 설명 후 기본 흐름은
이해했다.

하지만 새로운 형태의 질문에서:

``` text
onDelete는 부모에서 사용하는 것
```

으로 다시 혼동했다.

따라서 아직 완전히 자동화된 지식은 아니다.

> **팁:** 다음 복습에서는 설명을 다시 읽기보다 **새로운 컴포넌트
> 문제에서 함수 Props를 힌트 없이 직접 설계**해본다.

## 24.5 key와 일반 Props의 역할 구분

`key`를 `id` 전달과 연결해서 생각하는 혼동이 있었다.

현재 교정된 기준:

``` text
key
→ React 리스트 식별용
→ 일반 Props가 아님

id/product
→ 실제 자식에게 필요한 데이터
→ Props로 명시적으로 전달
```

> **팁:** 같은 `p.id`를 사용하더라도 **어디에 전달되느냐에 따라 역할이
> 다르다.**

# 25. 현재 독립 프로젝트 구현 어려움에 대한 중간 진단

현재까지의 복습만으로는 "JavaScript를 몰라서 프로젝트를 못 만든다"라고
단정할 수 없다.

오히려 현재 관찰된 패턴은 다음에 가깝다.

``` text
개별 문법
→ 상당 부분 사용 가능

작은 한 파일 기능
→ 직접 구현 가능

한 번 배운 패턴의 재적용
→ 가능

정확한 개념 설명
→ 상대적으로 어려움

여러 개념의 최초 조합
→ 인출 속도가 느림

컴포넌트가 나뉘었을 때
State / Props / 함수 흐름 설계
→ 보강 필요

요구사항을 정확한 UI 구조로 변환
→ 가끔 세부 조건 누락
```

따라서 앞으로 확인해야 할 핵심은 단순 문법 암기가 아니라:

``` text
요구사항 분석
↓
컴포넌트 분리
↓
State 후보 찾기
↓
State 위치 결정
↓
Props 데이터 흐름
↓
함수 Props 흐름
↓
Event
↓
State 업데이트
↓
UI 반영
```

을 **빈 프로젝트에서 스스로 설계할 수 있는가**이다.

> **팁:** 현재 단계에서는 "나는 코딩을 못한다"보다 **어느 설계 단계에서
> 생각이 멈추는가**를 계속 기록하는 것이 더 유용하다.

# 26. 다음 복습에서 재확인할 항목

다음날에는 오늘 내용을 처음부터 다시 설명받기보다, 새로운 문제 속에서
자연스럽게 재확인한다.

우선적으로 재시험할 내용:

1.  함수 Props를 힌트 없이 설계할 수 있는가
2.  State 위치를 스스로 결정할 수 있는가
3.  `map + 조건 + Object Spread`를 다시 사용할 수 있는가
4.  `key`와 데이터 Props를 구분할 수 있는가
5.  요구사항을 정확하게 컴포넌트/UI 구조로 옮길 수 있는가
6.  작성한 코드를 `왜 이렇게 했는지` 설명할 수 있는가
7.  컴포넌트가 여러 단계일 때 데이터/함수 흐름을 추적할 수 있는가

> **팁:** 다음 복습에서 기억이 조금 흐려져 있는 것은 오히려 좋다. 그
> 상태에서 스스로 다시 꺼낼 수 있는지를 확인해야 실제 학습 정도를 알 수
> 있다.

# 28. 오늘 복습 종료 시점

오늘은 여기까지 진행하고 다음날 이어서 복습한다.

현재 가장 중요한 것은 오늘 내용을 전부 암기하는 것이 아니라, 다음
복습에서 **힌트 없이 다시 꺼내 쓸 수 있는지 확인하는 것**이다.

특히 다음 세 가지는 다시 등장시킨다.

``` text
1. 함수 Props
2. State 위치 결정
3. 여러 개념을 조합한 State 업데이트
```
