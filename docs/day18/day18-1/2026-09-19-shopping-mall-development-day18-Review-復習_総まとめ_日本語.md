## 2. HTML / CSS / JavaScript の役割

### HTML

Webページの**構造とコンテンツ**を作る。

### CSS

HTMLで作った構造の**見た目・配置・デザイン**を担当する。

### JavaScript

ユーザー操作への反応やデータ変更など、**動作とロジック**を担当する。

``` text
HTML → 構造 / コンテンツ
CSS → 表現 / デザイン
JavaScript → 動作 / ロジック
```

> **ヒント:** 「画面 / 装飾 / 機能」だけでなく、**構造 / 表現 /
> 動作**として覚える。

------------------------------------------------------------------------

## 3. Reactを使う理由

Vanilla
JavaScriptでは、データ変更後にDOMを直接探して更新する処理が必要になることが多い。Reactでは**StateとUIの関係を宣言的に管理**できる。

``` text
State変更
↓
Re-render
↓
新しいStateを基準にUIを計算
↓
UIへ反映
```

Reactの利点は単にコードを短くすることではなく、**変化するデータ(State)と画面(UI)の関係を体系的に管理すること**にある。

> **ヒント:**
> Reactを「DOM操作をしなくてよいもの」だけでなく、**Stateの変化からUI更新までをつなぐ仕組み**として理解する。

------------------------------------------------------------------------

## 4. DOM

DOMは、ブラウザがHTML文書をプログラムから扱えるように**オブジェクト／ツリー構造として表現したインターフェース**である。JavaScriptが画面を変更するとき、元のHTMLファイルそのものを書き換えるのではなく、ブラウザ上のDOMを操作する。

> **ヒント:**
> `HTMLファイル = DOM`ではない。ブラウザがHTMLを解析してDOMを作る。

------------------------------------------------------------------------

## 5. useState と Re-render

``` jsx
const [count, setCount] = useState(0);
```

``` text
count → 現在のState
setCount → Stateを更新する関数
0 → 初期値
```

``` text
count = 0
↓
setCount(count + 1)
↓
State = 1
↓
Re-render
↓
UIに1が反映
```

`useState(0)`の`0`は最初のState生成時に使われる初期値であり、その後はReactが現在のStateを保持する。

> **ヒント:**
> `useState = 画面の値を変えるもの`だけでなく、**コンポーネントが覚える必要のある変化するデータとUI更新を結びつけるもの**と理解する。

------------------------------------------------------------------------

## 6. Counterの自力実装

``` jsx
import { useState } from "react";

export default function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>increase</button>
    </div>
  );
}
```

自分で判断できた流れ:

``` text
変化する値 → count
↓
Stateが必要
↓
初期値0
↓
クリックEvent
↓
setCount
↓
Re-render
↓
UI反映
```

JSXの最上位Wrapperや`export default`を一時的に忘れたが、現時点では核心的な概念不足より構文・構造の記憶問題に近い。

> **ヒント:**
> 小さな構文忘れと、機能構造そのものを設計できないことを区別する。

## 8. 配列StateとImmutability

``` jsx
const [fruit, setFruit] = useState(["りんご", "バナナ"]);
setFruit([...fruit, "オレンジ"]);
```

React
Stateは直接変更せず、**新しい配列・オブジェクトを作りSetterへ渡す**のが基本。

``` jsx
fruit.push("オレンジ");
```

は既存配列を直接変更する。

Spreadは「末尾へ追加」という意味ではない。

``` jsx
[...fruit, "オレンジ"] // 後ろ
["オレンジ", ...fruit] // 前
```

> **ヒント:**
> Spreadは「追加」ではなく、**配列要素やオブジェクトのプロパティを展開する構文**として覚える。

------------------------------------------------------------------------

## 9. map / filter / find

### map

各要素を目的の形へ変換し、**新しい配列を返す**。

### filter

条件を満たす要素だけを残し、**新しい配列を返す**。

``` jsx
products.filter((p) => p.id !== id)
```

### find

条件を満たす**最初の1要素**を返す。なければ`undefined`。

> **ヒント:** `map = 各要素を変換`, `filter = 条件に合うものを残す`,
> `find = 条件に合う1つを探す`。

------------------------------------------------------------------------

## 10. オブジェクト配列Stateの更新

最初に大きく詰まった部分の一つ。

``` jsx
function handleChangeAirpot() {
  const updatedProducts = product.map((p) => {
    if (p.name === "AirPods") {
      return {
        ...p,
        price: 50,
      };
    }
    return p;
  });

  setProduct(updatedProducts);
}
```

``` text
map → 新しい配列を作る
条件 → 更新対象を探す
...p → 既存プロパティを展開して新しいオブジェクトを構成
price: 50 → priceを上書き
return p → 対象外はそのまま
setProduct → 新しい配列でStateを更新
```

最初は`map + 条件 + Object Spread + Immutability + Setter`の組み合わせに時間がかかったが、一度修正した後は別問題で自力実装できた。

> **ヒント:** 複数概念が必要な機能は、**対象を探す → データを変換する →
> Stateを更新する**に分解する。

------------------------------------------------------------------------

## 11. Object Spread

``` js
const user = { name: "Tetsu", age: 20 };
const newUser = { ...user, age: 30 };
```

後に書かれた同名プロパティが前の値を上書きする。

``` js
const newUser = { age: 30, ...user };
```

なら最終的な`age`は`20`。

> **ヒント:**
> `...`自体が値を変更するのではなく、既存の要素・プロパティを展開し、**記述順序が最終結果に影響する**。

------------------------------------------------------------------------

## 12. filterによる削除

``` jsx
function handleDelete(id) {
  setProduct(product.filter((p) => p.id !== id));
}
```

``` text
削除対象の識別 → id
表示 → map
対象を除外 → filter
新しい配列 → setProduct
State変更 → UI変更
```

> **ヒント:**
> Reactでの削除は「元配列から直接消す」より、**削除対象を除外した新しい配列を作る**と考える。

------------------------------------------------------------------------

## 13. 更新 + 削除の組み合わせ

``` jsx
function handleAdd(id) {
  setProduct(
    product.map((p) =>
      p.id === id ? { ...p, price: p.price + 10 } : p
    )
  );
}

function handleDelete(id) {
  setProduct(product.filter((p) => p.id !== id));
}
```

再テストでは`id + map + 条件 + Object Spread + Setter + filter + Event`を自力で組み合わせられた。

> **ヒント:**
> 一度間違えたことより、**修正後に別問題へ自力で転用できたか**を重視する。

------------------------------------------------------------------------

## 14. Reactのkey

``` jsx
<ProductCard key={p.id} product={p} />
```

`key`はReactがリスト項目の**identity（同一性）を識別**するために使う。

``` text
key={p.id} → Reactのリスト識別
handleDelete(p.id) → 削除対象idを関数へ渡す
```

`key`は通常のPropsではないため、子で`props.key`として受け取れない。必要なら`id={p.id}`のように別途渡す。

> **ヒント:**
> `key = 子へidを渡すもの`ではなく、**React用のリスト識別情報**。

------------------------------------------------------------------------

## 15. Event Handlerと実行タイミング

``` jsx
onClick={() => handleDelete(p.id)}
```

はクリック時に実行する関数を渡す。

``` jsx
onClick={handleDelete(p.id)}
```

はレンダリング中に即時実行してしまう。

``` text
handleDelete → 関数そのもの
handleDelete() → 関数実行
```

> **ヒント:** Event
> Handlerには「今の実行結果」ではなく、**イベント発生時に実行する関数**を渡す。

------------------------------------------------------------------------

## 16. Props

Propsの本質はファイル分割ではなく、**コンポーネント間で値を渡すこと**。

``` jsx
<ProductCard product={product} />
```

同じファイル内のコンポーネント同士でもPropsは使う。

> **ヒント:**
> Propsを「別ファイルの値を取る方法」ではなく、**親コンポーネントから子コンポーネントへ値を渡す方法**として理解する。

------------------------------------------------------------------------

## 17. 関数もPropsで渡せる

``` jsx
<CounterButton onIncrease={handleIncrease} />
```

``` jsx
function CounterButton({ onIncrease }) {
  return <button onClick={onIncrease}>+1</button>;
}
```

``` text
親でhandleIncreaseを作る
↓
onIncreaseというPropsで子へ渡す
↓
子がonIncreaseを実行
↓
親のhandleIncreaseが実行
↓
親のStateが変更
```

> **ヒント:**
> 「関数Props」という別機能ではなく、**Propsとして渡す値が関数であるだけ**。

------------------------------------------------------------------------

## 18. データProps + 関数Props

``` jsx
<ProductCard
  product={p}
  onDelete={handleDelete}
/>
```

``` text
product → 表示に使うデータProps
onDelete → 子から実行する関数Props
```

重要な区別:

``` text
関数を作った場所 → 親
Propsとして受け取る場所 → 子
実行する場所 → 子のEvent
変更されるState → 親のState
```

> **ヒント:** 親で作った関数でも、Propsで渡せば子から実行できる。

------------------------------------------------------------------------

## 19. 複数段階のProps

``` text
App
↓ handleDelete
ProductList
↓ handleDelete
ProductCard
↓
削除ボタン
↓
親のhandleDelete
↓
AppのState変更
```

中間コンポーネントが直接使わなくても、下位の子が必要なら受け取って再度渡すことがある。

> **ヒント:**
> 深い構造では、まず**Stateの位置とPropsの移動経路を矢印で描く**。

## 20. Stateをどこに置くか

``` text
App
├── Header       ← cart件数が必要
└── ProductList
    └── ProductCard ← cart追加が必要
```

この場合、`cart`は共通の親である`App`で管理するのが自然。

重要なのは「Stateを常に最上位へ」ではなく、

> **そのStateを必要とするコンポーネントたちの適切な共通親に置く。**

> **ヒント:** **必要な分だけ上へ**Stateを持ち上げる。

------------------------------------------------------------------------

## 21. Stateを上げなくてよい場合

`quantity`を`QuantitySelector`だけが使うなら、その中に置けばよい。

しかし`ProductInfo`も同じ`quantity`を必要とするようになれば、共通親の`ProductPage`へStateを上げる。

これは**Lifting State Up**につながる。

> **ヒント:**
> Stateの位置は固定ではなく、**誰がそのデータを必要とするか**で変わる。

## 25. 自力プロジェクト実装が難しい理由の中間診断

現時点では「JavaScriptを知らないから作れない」とは言えない。

観察された傾向:

``` text
個別構文 → かなり使用可能
小さな1ファイル機能 → 自力実装可能
学んだパターンの再適用 → 可能
正確な概念説明 → 相対的に難しい
複数概念の初回組み合わせ → 取り出しが遅い
コンポーネント分割後のState / Props / 関数設計 → 強化が必要
要件→正確なUI構造 → 細部を落とす場合あり
```

今後確認すべき中心は:

``` text
要件分析
↓
コンポーネント分割
↓
State候補
↓
State位置
↓
データProps
↓
関数Props
↓
Event
↓
State更新
↓
UI反映
```

を空のプロジェクトから自力で設計できるかどうか。

> **ヒント:**
> 「できない」と一括りにせず、**どの設計段階で思考が止まるのか**を記録する。
