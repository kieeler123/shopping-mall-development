# Day 31~40 — Next.js + TypeScript 실전 프로젝트 로드맵

기존에 진행 중인 Next.js + TypeScript 주문 관리 프로젝트를 확장한다. 새로운 프로젝트를 시작하지 않는다.

> **학습 방향: 핵심 이론 → 객관식 1문제 → 프로젝트 구현 → 코딩 테스트 1문제 → 검사 및 기록**

## 하루 학습 루틴 (120분)

| 단계 | 시간 |
|---|---:|
| 핵심 이론 | 20분 |
| 객관식 1문제 | 5분 |
| 실제 프로젝트 구현 | 65분 |
| 코딩 테스트 1문제 | 20분 |
| TypeScript·ESLint 검사 및 기록 | 10분 |

## Day 31–40

| Day | 주제 | 핵심 이론 | 객관식 1문제 | 실제 프로젝트 작업 | 마지막 코딩 테스트 1문제 | 완료 목표 |
|---|---|---|---|---|---|---|
| **Day 31** | 기존 프로젝트 분석과 Client / Server 구분 | 현재 프로젝트 구조, Server/Client Component, Route Handler 역할 | Route Handler와 Client Component의 차이는? | 파일 구조와 주문 데이터 흐름 분석, 책임 불명확한 부분 정리 | 클라이언트 전용 로직을 적절한 컴포넌트에 배치 | 파일별 데이터 흐름을 설명 |
| **Day 32** | Route Handler와 GET API | route.ts, GET(), Response.json() | GET Route Handler의 주요 역할은? | 기존 /api/orders 점검 및 JSON 응답 개선 | 주문 배열을 반환하는 GET Handler 작성 | API 호출 및 응답 확인 |
| **Day 33** | HTTP 상태 코드와 오류 처리 | Request/Response, response.ok, 200/400/404/500 | 요청 실패에 맞는 상태 코드는? | GET API 성공/실패 응답과 UI 오류 표시 개선 | response.ok와 try/catch를 포함한 요청 함수 수정 | 요청 실패 시 오류 UI 확인 |
| **Day 34** | 동적 Route와 PATCH | 동적 경로, URL 파라미터, PATCH, 입력 검증 | /api/orders/123의 ID를 어떻게 처리할까? | 주문 상태 변경 API와 updateOrderStatus 연결 | PATCH Handler의 핵심 업데이트 로직 작성 | 서버와 UI의 주문 상태 일치 |
| **Day 35** | POST와 주문 등록 | POST, JSON Body, 폼 상태, 서버 입력 검증 | 요청 본문은 서버에 어떻게 전달될까? | 주문 등록 폼과 POST API 연결 | 입력값 검증 및 주문 생성 함수 작성 | 신규 주문을 목록에서 확인 |
| **Day 36** | DELETE와 주문 삭제 | DELETE, 삭제 대상 식별, 실패 처리 | 삭제 실패 시 UI는 어떻게 동작해야 할까? | 삭제 버튼·확인·API·목록 갱신 연결 | 성공한 경우에만 목록을 갱신하는 삭제 함수 | 선택한 주문 삭제 및 실패 표시 |
| **Day 37** | DB와 영구 저장 | DB, 테이블, 기본 키, CRUD, 영속성 | 메모리 배열과 DB 저장의 차이는? | 기존 저장소를 확인하고 필요시 DB 연동 | ID 기반 조회 또는 수정 데이터 접근 함수 | 재시작 후 데이터 유지 |
| **Day 38** | 검색·필터·정렬 | filter, sort, URL 쿼리, 클라이언트/서버 필터링 | 상태별 주문 필터링 방법은? | 주문 검색·상태 필터·최신순 정렬 구현 | 필터링·정렬 함수 작성 | 원하는 주문 탐색 |
| **Day 39** | 실전 디버깅과 테스트 | 정적 분석과 동작 테스트, 테스트 기본 구조 | TS/ESLint/테스트가 각각 잡는 오류는? | CRUD 주요 기능과 실패 경로 검증 | 버그가 있는 주문 관리 함수 수정 | 주요 기능·오류 처리 검증 |
| **Day 40** | 통합·리팩터링·1차 완성 | 관심사 분리, 중복 제거, 유지보수 | 컴포넌트와 Custom Hook의 책임은? | 기능 통합 점검, 구조 정리, README 작성 | 중복 로직을 Hook 또는 함수로 분리 | 기능 시연 및 데이터 흐름 설명 |

팁: 이미 구현된 기능은 재작성하지 말고 점검·개선한다. 프로젝트 난이도에 따라 하루 분량을 조정한다.

## 평가 기준

- 객관식 1문제: 20점
- 실제 프로젝트 구현·검증: 50점
- 코딩 테스트 1문제: 30점
- 권장 통과 기준: 80/100점. 실제 동작을 우선한다.

## Day 40 완료 기준

- 서버 주문 조회
- 주문 등록·상태 수정·삭제
- 검색·필터·정렬
- 영구 저장
- Loading / Error / Empty / Success
- 타입 검사·린트·핵심 동작 검증
- 데이터 흐름 설명과 README
