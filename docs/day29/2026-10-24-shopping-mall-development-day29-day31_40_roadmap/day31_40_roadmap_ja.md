# Day 31〜40 — Next.js + TypeScript 実践プロジェクト計画

すでに開発中の Next.js + TypeScript 注文管理プロジェクトを拡張する。新しいプロジェクトは作成しない。

> **学習の流れ：重要な理論 → 四択1問 → プロジェクト実装 → コーディング課題1問 → 検査・記録**

## 毎日の学習ルーティン（120分）

| 内容 | 時間 |
|---|---:|
| 重要な理論 | 20分 |
| 四択問題1問 | 5分 |
| プロジェクト実装 | 65分 |
| コーディング課題1問 | 20分 |
| TypeScript・ESLint 検査と記録 | 10分 |

## Day 31–40

| Day | テーマ | 重要な理論 | 四択問題1問 | プロジェクト作業 | 最後のコーディング課題1問 | 達成目標 |
|---|---|---|---|---|---|---|
| **Day 31** | 既存プロジェクト分析と Client / Server の区別 | App Router、Server/Client Component、Route Handler | Route Handler と Client Component の違いは？ | 既存ファイル構成と注文データの流れを確認し、責務を整理する | クライアント専用処理を適切なコンポーネントへ配置 | ファイルごとのデータフローを説明 |
| **Day 32** | Route Handler と GET API | route.ts、GET()、Response.json() | GET Route Handler の役割は？ | /api/orders を確認し JSON 応答を改善する | 注文一覧を返す GET Handler を作成 | API を呼び出して応答を確認 |
| **Day 33** | HTTP ステータスとエラー処理 | Request/Response、response.ok、200/400/404/500 | 失敗内容に適切なステータスコードは？ | API の成功・失敗応答と UI のエラー表示を改善 | response.ok と try/catch を使う関数を修正 | 失敗時にも安定したエラー画面を表示 |
| **Day 34** | 動的 Route と PATCH | 動的セグメント、URL パラメータ、PATCH、入力検証 | /api/orders/123 の ID をどう扱う？ | 状態更新 API と updateOrderStatus を接続 | PATCH 更新の主要処理を実装 | サーバーと UI の状態を一致させる |
| **Day 35** | POST と注文登録 | POST、JSON Body、フォーム状態、サーバー検証 | リクエスト本文はどうサーバーへ届く？ | 注文登録フォームと POST API を接続 | 入力検証と注文作成関数を実装 | 新規注文を一覧で確認 |
| **Day 36** | DELETE と注文削除 | DELETE、対象の識別、失敗処理 | 削除に失敗したら UI はどうする？ | 削除ボタン・確認・API・一覧更新を接続 | 削除成功時だけ一覧を更新する関数 | 対象の注文のみ削除し失敗を表示 |
| **Day 37** | DB と永続化 | DB、テーブル、主キー、CRUD、永続性 | メモリ配列と DB 保存の違いは？ | 現在の保存方法を確認し必要なら DB に接続 | ID による検索または更新のデータアクセス関数 | サーバー再起動後もデータが残る |
| **Day 38** | 検索・フィルター・並べ替え | filter、sort、クエリ、クライアント/サーバー検索 | 注文状態で絞り込むには？ | 注文検索・状態フィルター・新着順ソートを追加 | フィルターとソートの関数を作成 | 目的の注文を見つける |
| **Day 39** | 実践デバッグとテスト | 静的解析と動作テストの違い、テストの基礎 | TS・ESLint・テストは何を検出する？ | CRUD と失敗ケースを検証 | バグのある注文管理関数を修正 | 主要機能とエラー処理を確認 |
| **Day 40** | 統合・リファクタリング・一次完成 | 関心の分離、重複削減、保守性 | Component と Custom Hook の責務は？ | 機能を統合確認し構成を整理して README 作成 | 重複ロジックを Hook または関数に分離 | 機能を実演しデータフローを説明 |

ヒント：既存の機能を作り直さず、確認して改善する。実際の難易度に合わせて日程を調整する。
