Day 28 — 데이터 흐름과 상태 업데이트 총정리

실제 주문 관리 프로젝트 기반 복습 자료 · Next.js / React / TypeScript

1. 역할 분리

useOrders는 orders, isLoading, error와 updateOrderStatus를 제공한다. AdminOrdersPage는 Hook을 호출하고 OrderCard에 order와 onStatusChange를 전달한다. OrderCard는 select의 변경 이벤트에서 콜백을 호출한다.

학습 팁: 데이터 소유자, 화면 표시자, 변경 요청자를 구분해서 말해 보자.

2. 단방향 데이터 흐름

부모가 Props로 값을 자식에게 전달한다. 자식은 부모의 State를 직접 수정하지 않고 전달받은 Callback을 호출한다.

학습 팁: onStatusChange={updateOrderStatus}는 함수 전달, onStatusChange={updateOrderStatus()}는 렌더 중 호출이다.

3. 불변 업데이트

setOrders(prev => prev.map(order => order.id === updatedOrder.id ? updatedOrder : order))는 새 배열을 만들고 대상 주문 객체만 서버 응답으로 교체한다.

학습 팁: map은 배열을 새로 만들지만 변경하지 않은 요소의 객체 참조는 그대로 재사용한다.

4. API와 오류

PATCH /api/orders/{id} 후 response.ok를 검사한다. 성공 시 response.json()의 updatedOrder로 State를 갱신하고 Order를 반환한다. 실패 시 error를 저장하고 null을 반환한다.

학습 팁: fetch는 HTTP 4xx/5xx 응답 자체로 reject되지 않는다. response.ok를 확인하자.

5. TypeScript

실제 Hook 시그니처는 (id: number, status: OrderStatus) => Promise<Order | null>이다. OrderCard의 void 콜백 타입도 반환값을 무시하는 자리에서는 허용되지만 결과를 처리하려면 Promise 타입을 명시하는 편이 명확하다.

학습 팁: Promise<Order | null>을 호출한 뒤 null 여부로 실패를 판별할 수 있다.

6. 제어 컴포넌트

OrderCard의 select value={order.status}는 Props를 기준으로 표시된다. PATCH 성공과 setOrders 이후 새로운 Props가 내려오면 선택값이 바뀐다.

학습 팁: UI 값과 서버 값의 동기화 순서를 말로 설명해 보자.

7. 발견한 UX 주의점

PATCH 오류가 error를 설정하면 AdminOrdersPage의 !error 조건 때문에 주문 카드 목록이 숨겨진다. 또한 PATCH 진행 중 별도 loading 상태나 중복 요청 방지는 없다.

학습 팁: 목록 조회 오류와 상태 변경 오류를 분리하는 개선은 가능하지만 Day 28에서는 기존 코드를 함부로 수정하지 않았다.

8. 오늘 답안의 보완점

템플릿 리터럴은 백틱을 써야 한다. fetch 옵션 객체에서 쉼표를 확인한다. setUpdatedId와 setUpdatingId처럼 변수명이 어긋나지 않게 한다. catch의 unknown을 string으로 변환해 setError에 전달한다.

학습 팁: 코드를 쓴 뒤 URL, 쉼표, 변수명, 타입 네 가지를 점검하자.

실제 실행 흐름

AdminOrdersPage → OrderCard → onStatusChange → updateOrderStatus → PATCH API → response.ok → updatedOrder → setOrders(map) → React render
