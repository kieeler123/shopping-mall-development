Day 28 — データフローと状態更新・総復習

実際の注文管理プロジェクトに基づく復習教材 · Next.js / React / TypeScript

1. 責務の分離

useOrders は orders、isLoading、error、updateOrderStatus を提供する。AdminOrdersPage は Hook を呼び出し、order と onStatusChange を OrderCard に渡す。OrderCard は select の変更時にコールバックを呼ぶ。

学習のコツ: データの管理者、表示担当、変更要求者を分けて説明しよう。

2. 単方向データフロー

親から子へ Props で値を渡す。子は親の State を直接変更せず、受け取ったコールバックを呼び出す。

学習のコツ: onStatusChange={updateOrderStatus} は関数を渡す。() を付けるとレンダー中に呼び出してしまう。

3. イミュータブルな更新

setOrders(prev => prev.map(order => order.id === updatedOrder.id ? updatedOrder : order)) は新しい配列を作り、対象の注文だけサーバー応答に置き換える。

学習のコツ: map は新しい配列を作るが、変更しない要素のオブジェクト参照は再利用する。

4. API とエラー

PATCH /api/orders/{id} の後で response.ok を確認し、成功時に updatedOrder で State を更新して Order を返す。失敗時はエラーを保存して null を返す。

学習のコツ: fetch は HTTP 4xx/5xx の応答だけでは reject しない。

5. TypeScript

Hook の型は (id: number, status: OrderStatus) => Promise<Order | null>。戻り値を無視する void 型のコールバックにも渡せるが、結果を扱うなら Promise 型を明示すると分かりやすい。

学習のコツ: await 後に null を判定しよう。

6. 制御コンポーネント

OrderCard の select は value={order.status} によって制御される。PATCH 成功後、setOrders で新しい Props が渡されると表示値が更新される。

学習のコツ: サーバーから UI までの更新順序を言葉で説明しよう。

7. UX の注意点

PATCH 失敗時に error が設定されると、AdminOrdersPage の !error 条件によって注文カード全体が非表示になる。また PATCH 中の個別ローディングや重複リクエスト防止はない。

学習のコツ: 一覧取得エラーと更新エラーの分離は今後の改善候補。Day 28 では不要な変更をしない。

8. 今日の解答での改善点

URL の変数展開にはバッククォートを使う。fetch のオプション内のカンマを確認する。setter 名を統一し、catch の unknown を文字列に変換して setError に渡す。

学習のコツ: URL、カンマ、変数名、型を最後に確認しよう。

実際の実行フロー

AdminOrdersPage → OrderCard → onStatusChange → updateOrderStatus → PATCH API → response.ok → updatedOrder → setOrders(map) → React render
